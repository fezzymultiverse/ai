# V1.99.118 - Video player: failures are visible, 3 routes, RETRY

Built on V1.99.117. Web files only (no Kotlin change): a normal `npx cap sync android` and rebuild is enough.

PROBLEM (from the code, not from a phone)
- When the video would not start, horizon_watch.js wrote the reason and then closed the card straight away, so you saw an empty panel.
- yt.watch asked YouTube for ONE stream and gave up. yt.play (music) already tries 3 routes and a chunk-download fallback.

CHANGES
- horizon_watch.js: a failed start keeps the card open. The picture shows COULD NOT PLAY plus the real reason (player error 1-4 with its name, or "no picture after 15 seconds (ready N, net N)") and a RETRY button. X closes it.
- index.html (ytWatchTool): up to 3 attempts, each on a different YouTube route (skip list, same as yt.play). Each attempt is recorded; the AI is told every route's reason and must not claim it played.
- HorizonWatch.report(): trail of the last attempts, e.g. "try 1 vr direct: player error 4 (source not supported) | try 1 vr download: ok".
- Cache-buster ?v= bumped to 1.99.118 so the WebView does not serve the old horizon_watch.js.
- tests/watch-v118.test.cjs (3 checks, includes a fake-DOM run of fail -> card stays -> RETRY fires -> X closes).

TESTS
- Full suite: 294 pass, 4 fail exactly as on V1.99.116/117 (edge-kit restore, paid-APIs-gone, native check-ins, OpenRouter seed).
- NOT tested on a phone. It cannot be proven here that YouTube serves the video. What it guarantees: you will now SEE why, and it tries 3 routes.

IF IT STILL FAILS
- Screenshot the red panel. The text names the route and the error code, which is what the next fix needs.

NOT DONE (next, if you want it)
- Folder picker (Android "Choose folder") so you never type a path.
- Verify-after-move: the app checks the file exists at the destination and reports that, not the AI's word.
