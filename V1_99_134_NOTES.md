HORIZON V1.99.134 - SMALL-MODEL SCAFFOLD + BIGGER-MODEL ESCALATION

Problem: small or weak models do not follow tool tags reliably, and a rate-limited or empty API leaves a tool job half done.

1) Scaffold (www/horizon_studio.js, hooked in index.html nativePre)
- When the message is a playlist request (make / create / build / queue up / play / download ... playlist) and YouTube is on, the APP reads it: play or download or both, song count (default 10, 4-20).
- The model is asked ONE narrow thing: "list N real songs, Artist - Song, nothing else". The app cleans the reply (numbering, bullets, bold, chatter, duplicates, "(Official Video)"). If fewer than 4 songs come back it retries once with a stricter prompt; if still not, it falls back to the normal chat flow.
- The app then builds the playlist.create call itself (name derived from the request, made distinct), plays first, then saves into Download/Horizon/<name>/ numbered. The chat model only reports the real result.
- Download requests are only scaffolded when File access is on.

2) Escalation (index.html escalatedAsk / strongCandidates)
- The song-list question goes first to a bigger model the user already has a key for (up to 2 other ready providers whose selected model name looks large: 70B+ sizes, large/pro/opus/sonnet, GPT-4/5, Gemini Pro, DeepSeek V3/R1, Qwen3 32B+, Mistral Large, Command R+, Kimi K2, GLM 4.5+). 45 s timeout each. A failure, quota/429, timeout or a reply with fewer than 4 songs moves to the next one.
- The provider he is chatting with is always the last resort. The Horizon Worker and AI Horde are never used for escalation. Switched-off providers are skipped. Off switch: localStorage horizon_escalate = '0'.
- The tool result tells the AI (and so you) which provider supplied the song list.

Only the playlist job is scaffolded and escalated so far. Move/rename file plans, downloads and podcasts still go through the normal model flow; they are the next candidates.
